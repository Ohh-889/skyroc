# 证据读取顺序

目标是先确认当前事实，再设计体验。不要从单一参考项目直接推导最终页面。

## 1. 用户输入

先整理用户明确提供的：

- 目标模块和期望产物。
- 设计文档、PRD、原型、Java、FastAPI、React 路径。
- 明确要求的页面数量和命名。
- 只做设计还是还要实施生产代码。

用户指定路径是本次任务的首要范围。不要擅自扩大到无关模块。

## 2. 仓库级约束

读取最近的 `AGENTS.md`、设计系统和信息架构：

```text
AGENTS.md
design/ruoyi-plus-fast/design-system.md
design/ruoyi-plus-fast/design/04-feature-map.md
design/ruoyi-plus-fast/design/05-information-architecture.md
design/ruoyi-plus-fast/design/07-page-registry.md
```

只读取与当前页面决策有关的设计文档。已有文档与运行时不一致时，把差异记录为设计或实现漂移。

## 3. 相邻 PRD 和原型

至少选择：

- 两个业务形态相近的 PRD。
- 两个视觉或交互形态相近的 HTML 原型。

选择依据优先于目录距离。例如，带树形筛选的页面应优先参考用户或菜单页面，密钥配置页面应优先参考 OSS 配置，而不是机械参考文件名最接近的页面。

需要提取：

- 文档章节和事实表达方式。
- 页面壳层尺寸、筛选区、表格区、抽屉和弹窗模式。
- 危险操作、空状态、加载状态和反馈方式。
- 移动端降级策略。

## 4. Java RuoYi 参考

从用户指定的 Java/Plus UI 根目录搜索：

- `src/views/**/index.vue`
- 同目录组件、类型和 API 文件。
- 对应 Controller、Service、DTO/VO、权限注解。

提取业务能力，不复制 Element Plus 视觉。记录：

- 查询条件、表格列和表单字段。
- 行操作和批量操作。
- 接口路径、请求方式和权限字符。
- 系统记录保护、唯一性校验、状态变更和删除约束。

Java 参考只能说明来源系统的行为，不能证明当前 FastAPI 已实现。

## 5. 当前 FastAPI

从当前目标后端重新读取：

- `routes.py` 或路由包。
- 请求/响应 schema。
- service、use case、repository 和 model。
- 权限依赖、错误映射和测试。

至少核对：

- 实际 HTTP 方法和路径。
- 查询、路径和请求体字段。
- 响应包裹结构、分页结构和字段可空性。
- 权限字符与租户边界。
- 业务校验、受保护记录和错误状态。
- 已实现、部分实现和未实现能力。

接口事实必须来自代码或当前接口文档，不从旧 PRD 反向推断。

## 6. 当前 React

如果目标页面或 API 封装已经存在，读取：

- TanStack Router 路由与菜单路径。
- 页面组件、局部组件和查询参数。
- API 类型、请求函数和 TanStack Query 封装。
- 权限组件、字典、状态映射和共用 UI。

记录现有实现可复用部分和与后端不一致之处。不要为了原型顺手修改生产页面。

## 7. 证据冲突处理

按以下原则裁决：

1. 当前 FastAPI 决定“现在能够联调什么”。
2. 当前产品设计系统决定视觉和交互语言。
3. 当前 React 决定已有实现和接入成本。
4. Java RuoYi 决定业务参考边界。
5. 旧 PRD 和旧原型是历史设计证据，不是实时接口契约。

不能确定时，在 PRD 中写成“设计假设”或“待后端补齐”，不要伪装为事实。

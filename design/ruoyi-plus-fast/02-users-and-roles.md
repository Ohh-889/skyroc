# Skyroc Admin 用户与角色

## 1. 文档目的

本文定义产品设计阶段需要覆盖的候选用户类型、职责、目标和权限边界，用于指导首页、导航、工作流和权限页面设计。

本文描述的是产品角色，不等同于当前后端已经存在的角色编码。正式权限矩阵需要在后端角色、按钮权限和数据范围确认后更新。

## 2. 角色建模原则

角色设计需要分别回答：

1. 用户为什么进入系统。
2. 用户最常完成哪些任务。
3. 用户可以看到哪些数据。
4. 用户可以执行哪些操作。
5. 哪些操作需要审批、确认或审计。

不要只用“管理员”和“普通用户”覆盖所有场景，也不要为每个岗位创建完全不同的界面。

## 3. 候选角色

### 3.1 企业管理员

**定位**

负责企业级账号、组织和权限治理，对企业范围内的配置结果负责。

**主要目标**

- 建立和维护组织结构。
- 创建、启用、停用企业成员。
- 分配角色和数据范围。
- 查看重要系统状态和风险事件。

**高频任务**

- 查看新增或异常账号。
- 调整用户角色。
- 处理部门和岗位变化。
- 检查敏感权限配置。

**设计关注点**

- 首页需要突出组织、账号和风险状态。
- 权限变更必须展示影响对象和变更结果。
- 批量操作必须明确数量和范围。

**状态**

候选角色，待确认是否与系统管理员合并。

### 3.2 系统管理员

**定位**

负责系统运行配置、菜单、字典、参数和技术性管理能力。

**主要目标**

- 维护系统配置。
- 配置菜单和功能入口。
- 排查登录、权限和运行异常。
- 管理影响全局的系统参数。

**高频任务**

- 查询操作日志和登录日志。
- 修改系统参数。
- 检查菜单和权限配置。
- 处理账号登录问题。

**设计关注点**

- 全局配置需要清晰区分普通设置和高风险设置。
- 修改前后值需要可追溯。
- 技术字段需要提供人类可读解释。

**状态**

候选角色，职责边界待确认。

### 3.3 业务运营人员

**定位**

使用后台处理日常业务、查询数据和执行受控运营操作。

**主要目标**

- 快速找到待处理任务。
- 查询和筛选业务数据。
- 完成新增、修改、审核或状态处理。
- 查看与本人业务相关的结果。

**高频任务**

- 使用多条件筛选定位数据。
- 查看详情和历史记录。
- 执行单条或批量业务操作。
- 导出授权范围内的数据。

**设计关注点**

- 首页和导航突出高频业务入口。
- 列表筛选、状态和批量操作需要高效。
- 返回列表时应尽可能保留筛选和分页上下文。

**状态**

候选角色，具体业务域待定义。

### 3.4 普通员工

**定位**

以查看个人信息、处理个人任务和使用少量自助功能为主。

**主要目标**

- 查看与本人相关的信息。
- 修改允许自助维护的资料。
- 处理个人待办或通知。
- 管理账号安全设置。

**设计关注点**

- 不展示与本人无关的管理菜单。
- 避免将后台配置术语暴露给普通员工。
- 首页更接近个人工作入口，而不是系统监控台。

**状态**

候选角色，是否需要登录管理后台待确认。

### 3.5 审计或安全人员

**定位**

查看敏感操作、登录风险和权限变更记录，原则上以只读为主。

**主要目标**

- 检索关键操作记录。
- 追踪权限和配置变更。
- 识别异常登录和高风险行为。
- 导出合规所需记录。

**设计关注点**

- 日志检索和时间范围筛选必须高效。
- 操作主体、对象、时间和结果需要清晰。
- 原始数据与人类可读摘要需要兼顾。

**状态**

候选角色，是否进入首期待确认。

| 查看个人资料   | 需要       | 需要       | 需要           | 需要       | 需要         |

## 5. 数据范围维度

正式角色设计前需要确认系统是否支持以下数据范围：

- 全部数据。
- 当前企业或租户。
- 当前部门及下级部门。
- 当前部门。
- 仅本人创建或负责的数据。
- 自定义组织范围。
- 按业务对象单独授权。

如果数据范围由后端决定，页面仍需要向用户解释当前看到的数据范围，尤其是在列表为空、导出数量受限或操作被拒绝时。

## 6. 首页差异原则

不建议为每个角色创建完全独立的首页。优先采用同一工作台结构，根据权限和职责组合不同模块：

- 企业管理员：组织概览、账号风险、权限变更、系统公告。
- 系统管理员：系统状态、配置变更、异常日志、快捷维护入口。
- 业务运营：待办、常用业务入口、近期处理、业务指标。
- 普通员工：个人待办、通知、个人资料和账号安全。
- 审计人员：风险事件、敏感操作、审计查询入口。

## 7. 权限体验原则

1. 无权限功能原则上不进入导航。
2. 用户通过外部链接进入无权限页面时展示 403，而不是 404。
3. 页面内无权限操作是隐藏还是禁用，需要按“是否有必要让用户知道功能存在”决定。
4. 被禁用操作需要提供原因，不能只显示灰色按钮。
5. 权限变更需要显示影响对象、影响范围和生效结果。
6. 超级管理员能力不应成为普通角色设计的默认前提。

## 8. 待确认问题

| 编号     | 问题                                 | 影响               |
| -------- | ------------------------------------ | ------------------ |
| ROLE-001 | 企业管理员和系统管理员是否是不同角色 | 首页和导航         |
| ROLE-002 | 普通员工是否进入本后台               | 产品范围           |
| ROLE-003 | 是否支持多租户                       | 用户和数据隔离     |
| ROLE-004 | 是否支持部门级数据权限               | 角色配置和列表结果 |
| ROLE-005 | 是否存在审批角色                     | 核心业务流程       |
| ROLE-006 | 审计人员是否只能读取                 | 日志页面操作       |
| ROLE-007 | 角色是否允许一个用户多选             | 用户编辑和授权流程 |
| ROLE-008 | 权限变更是否立即生效                 | 操作反馈和会话处理 |

## 9. 后续输出

角色确认后需要补充：

- 正式角色定义。
- 角色与模块访问矩阵。
- 角色与页面操作矩阵。
- 数据范围矩阵。
- 各角色首页模块优先级。
- 关键高风险操作责任人。

## 2. 架构结论

用户管理不是一张独立用户表，而是以下能力的组合入口：

```text
部门范围筛选
  → 用户检索与分页
  → 用户身份资料维护
  → 部门、岗位和角色关联
  → 启用、停用、删除和密码重置
  → 会话、权限缓存和审计联动
```

页面职责：

- 前端负责查询条件、选择状态、表单交互、权限显隐和操作结果展示。
- 用户管理用例负责租户隔离、数据范围、唯一性、密码处理、关联表更新和事务边界。
- 部门模块负责返回当前操作者可见且可选择的部门，不由前端根据完整组织树推断权限。
- 角色和岗位模块负责返回可分配选项及禁用原因，不由用户页面复制其业务规则。
- 认证与会话模块负责在停用、删除、重置密码或权限变化后执行既定的会话失效策略。
- 操作日志记录敏感变更，不在页面请求中提交操作者、租户或审计字段。

页面采用：

```text
可折叠部门导航 + 查询区 + 分页表格
  + 用户详情抽屉
  + 新增/编辑抽屉
  + 安全操作弹窗
```

不把用户详情、编辑、角色和安全操作全部堆进一个对话框。资料编辑、权限分配和账号安全的风险不同，提交边界也不同。

## 3. 已知事实

### 3.1 产品与设计事实

- 用户管理是企业管理员维护成员和系统管理员处理账号问题的核心入口。
- 页面需要支持查询、详情、新增、编辑、启用、停用、删除、重置密码和分配角色。
- 用户归属一个部门，可以关联多个岗位和多个角色。
- 列表结果必须受当前租户、按钮权限和角色数据范围约束。
- 当前应用尚未实现正式的用户、角色和岗位管理页面。
- 现有信息架构使用 `/system/users`，RuoYi 的 `/system/user` 只作为参考路径，不改变本项目路由命名。

### 3.2 RuoYi 参考实现事实

参考实现已经包含：

- 左侧部门树和部门名称过滤。
- 用户账号、昵称、手机号、状态和创建时间查询。
- 用户分页、列设置、批量选择、导入和导出。
- 新增和编辑用户时选择部门、岗位和角色。
- 从配置 `sys.user.initPassword` 读取初始密码并预填表单。
- 表格内状态开关、删除、重置密码和分配角色。
- 部门变化后重新加载岗位选项。

这些能力是业务覆盖面的参考，不代表交互方式需要原样复制。本设计调整以下行为：

- 状态不使用可误触的行内开关，改为带影响说明的明确操作。
- 不把新密码拼进普通成功消息。
- 不在前端预填或展示全局统一初始密码。
- 单行操作最多显示三个，其余进入“更多”菜单。
- 部门筛选明确区分“仅当前部门”和“包含下级部门”。
- 角色调整与基础资料保存分开，避免普通资料修改意外覆盖权限关联。

### 3.3 当前后端模型事实

`User` 模型已经确定：

| 字段          | 页面含义         | 页面规则                               |
| ------------- | ---------------- | -------------------------------------- |
| `id`          | 用户 ID          | 只读，不作为主要识别信息               |
| `tenant_id`   | 所属租户         | 服务端上下文确定，前端不提交           |
| `dept_id`     | 所属部门         | 可空；选择范围由服务端返回             |
| `username`    | 用户账号         | 租户内唯一，创建后默认不可修改         |
| `nickname`    | 用户昵称         | 用户的主要展示名称                     |
| `user_type`   | 用户类型         | 首期不开放编辑，使用后端默认值         |
| `email`       | 邮箱             | 可空，最长 50 个字符                   |
| `phonenumber` | 手机号           | 可空，最长 11 个字符                   |
| `sex`         | 性别             | `0` 男、`1` 女、`2` 未知               |
| `avatar`      | 头像文件 ID      | 列表显示，上传归个人资料能力           |
| `password`    | 密码哈希         | 永不返回前端，前端只提交一次性明文输入 |
| `status`      | 账号状态         | `0` 正常、`1` 停用                     |
| `login_ip`    | 最后登录 IP      | 详情只读，按权限脱敏或隐藏             |
| `login_date`  | 最后登录时间     | 列表和详情只读                         |
| `remark`      | 备注             | 可空，最长 500 个字符                  |
| `del_flag`    | 逻辑删除标志     | 前端不提交、不展示                     |
| 审计字段      | 创建与更新时间等 | 只读，前端不提交                       |

结构性规则：

- 账号唯一性是 `(tenant_id, username)`，跨租户可以重名，租户内不允许重名。
- 删除采用逻辑删除，并把账号归档为 `原账号#用户ID`，使同租户可以重新创建原账号。
- 超级管理员由受保护 ID 判定，不能仅依靠角色名称识别。
- 密码字段存储哈希；列表和详情接口不得返回密码字段。
- `UserPost` 和 `UserRole` 分别承载多岗位、多角色关联。
- 邮箱和手机号当前没有唯一约束；验证码登录已依赖这两个字段，实现管理接口前必须确认租户内重复策略。

### 3.4 当前后端能力边界

当前用户 Repository 和 Service 主要服务注册、登录身份查询、登录状态校验和最后登录记录，尚不具备完整的后台管理用例：

- 没有用户管理分页查询。
- 没有用户详情聚合接口。
- 没有后台新增、编辑、停用、删除和密码重置用例。
- 没有用户与角色、岗位关联的管理事务。
- 角色和岗位当前只有模型，尚未形成完整的可分配选项服务。

因此本文第 18 节接口均为目标契约，不是现有接口清单。

## 4. 页面目标

页面需要让有权限的管理员：

1. 在自己的数据范围内快速定位用户，而不是浏览整租户数据。
2. 看清用户的账号、部门、角色、状态和最近登录情况。
3. 创建用户并正确建立部门、岗位和角色关联。
4. 分开维护基础资料、角色授权和账号安全。
5. 在停用、删除、重置密码前理解对登录和权限的影响。
6. 执行批量操作时知道目标范围、成功数量和失败原因。
7. 遇到无权限、并发修改或后端规则拦截时得到可执行的反馈。

- 部门栏和用户内容位于同一内容卡片中，通过弱分隔线表达关系，不再套两层阴影卡片。
- 查询区默认展示高频条件，低频条件放入可展开区域。

- 分页、查询、部门选择和列设置写入 URL 查询参数或页面级持久状态，返回页面时恢复。

### 6.2 中等宽度

- `992px - 1199px` 自动收起部门栏，点击“部门”按钮打开临时侧栏。
- 隐藏联系方式和创建时间等低优先级列。
- 查询区只保留关键词、状态、查询和重置。
- 角色、创建时间等条件进入“更多筛选”。

### 6.3 窄屏

- `< 768px` 不承诺完整用户治理能力，只保证查询和查看详情。
- 部门树使用全屏抽屉，表格允许横向滚动。
- 默认列仅保留用户、部门、状态和操作。
- 新增和复杂授权提示在桌面端完成，不把多栏表单强行压缩为不可用的手机表单。

## 7. 部门导航

### 7.1 节点规则

- 顶部提供“全部用户”虚拟节点，它不是数据库部门。
- 树只显示当前操作者数据范围内可见的部门。
- 为构造路径而返回的只读祖先节点可以显示，但不可因此获得操作权限。
- 停用部门保留在筛选树中并显示状态标识，避免历史用户无法被定位。
- 部门搜索保留命中节点的祖先路径，并高亮真实命中节点。
- 节点名称过长时省略并通过 Tooltip 显示完整名称。

### 7.2 当前部门与下级范围

选择部门后必须明确范围：

| 模式         | 含义                                 | 默认值 |
| ------------ | ------------------------------------ | ------ |
| 仅当前部门   | 只查询 `dept_id` 等于所选部门的用户  | 否     |
| 包含下级部门 | 查询当前部门及全部可见子孙部门的用户 | 是     |

请求中显式提交 `includeChildren`，不能由前端把所有子部门 ID 展开后拼接请求。后端应使用部门树规则和数据权限计算最终范围。

从部门管理“查看成员”进入时：

```text
/system/users?deptId={deptId}&includeChildren=false
```

## 8. 查询设计

### 8.1 查询字段

| 字段     | 控件           | 规则                                       |
| -------- | -------------- | ------------------------------------------ |
| 关键词   | 输入框         | 匹配昵称、账号、手机号和邮箱；去除首尾空格 |
| 状态     | 单选下拉       | 全部、正常、停用                           |
| 角色     | 可搜索单选下拉 | 只显示当前操作者可见角色                   |
| 创建时间 | 日期范围       | 默认空；结束时间包含所选日期全天           |
| 最近登录 | 日期范围       | 放入更多筛选，首期可暂缓                   |

不同时放置“用户名称”和“用户昵称”两个外观相近的输入框。统一关键词提高检索效率；需要精确账号查询时，服务端支持 `username` 精确字段或关键词语法。

### 8.2 查询行为

- 点击查询或按 Enter 执行请求。
- 修改条件不自动请求，避免多条件筛选产生连续网络调用。
- 新查询将页码重置为 1。
- 重置清空关键词、状态、角色和时间，部门恢复“全部用户”。
- 查询条件通过 URL 表达，详情返回或浏览器前进后退时可恢复。
- 服务端返回的是权限裁剪后的总数，前端不显示租户真实总数作为对比。

### 8.3 空状态

首次没有任何用户：

```text
还没有用户
创建第一个用户并为其分配部门和角色
```

筛选无结果：

```text
没有找到符合条件的用户
尝试调整关键词、部门、状态或角色
```

只有具备新增权限时显示空状态主按钮“新增用户”。

## 9. 用户表格

### 9.1 列定义

| 列       | 默认显示 | 说明                                                   |
| -------- | -------- | ------------------------------------------------------ |
| 选择     | 是       | 仅可选择当前允许批量操作的用户                         |
| 用户     | 是       | 头像、昵称和账号两级信息；作为对象识别主列             |
| 部门     | 是       | 显示部门名称；无部门显示“未分配”                       |
| 角色     | 是       | 最多显示两个角色标签，剩余显示 `+N`                    |
| 联系方式 | 是       | 优先手机号，其次邮箱；按权限脱敏                       |
| 状态     | 是       | 文字加状态标识，不使用行内开关                         |
| 最近登录 | 是       | 相对时间，Tooltip 显示完整时间；从未登录显示“从未登录” |
| 创建时间 | 否       | 通过列设置开启                                         |
| 用户 ID  | 否       | 排障时通过列设置开启                                   |
| 操作     | 是       | 固定右侧                                               |

角色标签只表达当前角色，不直接推断最终权限。角色过多时通过 Popover 展示完整列表。

### 9.2 行交互

- 点击用户主列或“查看”打开详情抽屉。
- 行本身不整行可点击，避免与复选框和行操作冲突。
- 正常用户和停用用户使用相同文字对比度，状态差异由状态标识表达。
- 当前登录用户增加“当前账号”弱标签。
- 受保护超级管理员增加“受保护账号”标识，但不暴露内部判断方式。

### 9.3 行操作

| 操作        | 展示条件                 | 结果             |
| ----------- | ------------------------ | ---------------- |
| 查看        | 有查询权限               | 打开详情抽屉     |
| 编辑        | 有编辑权限且对象可编辑   | 打开编辑抽屉     |
| 分配角色    | 有授权权限且对象可授权   | 打开角色授权抽屉 |
| 启用 / 停用 | 有状态权限且对象允许变更 | 打开影响确认弹窗 |
| 重置密码    | 有重置密码权限           | 打开重置密码弹窗 |
| 删除        | 有删除权限且对象允许删除 | 打开危险确认弹窗 |

表格直接显示“查看”“编辑”，第三个位置按权限优先显示“分配角色”；其余进入“更多”。只有图标的按钮必须提供 Tooltip 和可访问名称。

## 10. 用户详情抽屉

### 10.1 展示结构

抽屉宽度建议 640px，包含：

```text
身份摘要
  头像 / 昵称 / 账号 / 状态 / 部门

基本资料
  手机 / 邮箱 / 性别 / 备注

组织与权限
  部门 / 岗位 / 角色

登录与安全
  最后登录时间 / 最后登录 IP / 在线设备入口（有权限时）

审计信息
  创建时间 / 更新时间 / 创建人 / 更新人
```

详情不展示密码、密码哈希、租户内部字段、逻辑删除字段和完整 Token 信息。

### 10.2 详情操作

- 顶部最多一个主操作“编辑资料”。
- “分配角色”“重置密码”“停用”和“删除”放在操作菜单或对应分区。
- 编辑成功后刷新详情与列表当前行，不关闭详情上下文。
- 用户已被其他管理员删除时，详情切换为对象不存在状态并提供返回列表入口。

## 11. 新增用户抽屉

### 11.1 字段

抽屉宽度建议 720px，字段按业务分组：

| 分组     | 字段         | 必填 | 规则                                         |
| -------- | ------------ | ---- | -------------------------------------------- |
| 账号信息 | 用户账号     | 是   | 2-30 个字符；禁用归档分隔符；租户内唯一      |
| 账号信息 | 用户昵称     | 是   | 最长 64 个字符                               |
| 账号信息 | 初始密码方式 | 是   | 系统生成或管理员设置，取决于后端安全策略     |
| 联系信息 | 手机号       | 否   | 最长 11 个字符；格式按真实业务地区规则       |
| 联系信息 | 邮箱         | 否   | 合法邮箱，最长 50 个字符                     |
| 联系信息 | 性别         | 否   | 默认未知，不默认男性                         |
| 组织关系 | 所属部门     | 否   | 仅允许选择正常且有权分配的部门               |
| 组织关系 | 岗位         | 否   | 可多选；选项随部门变化时明确提示并清理失效值 |
| 组织关系 | 角色         | 是   | 可多选；只允许分配有权管理的正常角色         |
| 其他     | 状态         | 是   | 默认正常                                     |
| 其他     | 备注         | 否   | 最长 500 个字符                              |

### 11.2 初始密码

不采用参考实现中“读取 `sys.user.initPassword` 后把统一密码预填到前端”的方式。统一初始密码容易泄漏，也会让多个新账号共享已知凭据。

目标方案：

1. 默认由服务端生成高强度临时密码。
2. 创建成功后只显示一次，并提供复制操作。
3. 普通接口和日志不得再次返回该密码。
4. 如果支持邀请链接，优先让用户自行设置密码。
5. 如果支持“首次登录强制改密”，需要后端增加明确状态字段，不能仅由前端提示模拟。

在上述后端能力落地前，可保留“管理员设置初始密码”作为首期兼容方案，但必须使用加密请求能力，不能读取和展示全局默认密码配置。

### 11.3 部门、岗位和角色加载

- 打开抽屉时并行加载部门、角色和通用岗位选项。
- 部门变化仅在岗位确实受部门约束时重新请求岗位。
- 因部门变化被移除的岗位必须在字段下方明确提示，不能静默丢失。
- 角色或岗位在编辑期间被停用时保留已选项并标记“已停用”，保存时由后端决定是否允许保留。
- 任一选项接口失败时保留已填写内容，提供局部重试，不关闭抽屉。

## 12. 编辑用户抽屉

- 账号默认只读；如业务允许改账号，需要独立权限、唯一性校验和审计记录。
- 编辑只提交基础资料、部门、岗位和状态，不同时提交角色列表。
- 当前用户编辑自己时，不在本页面修改自己的部门、岗位、角色和状态。
- 受保护账号的不可编辑字段由服务端返回能力标记，前端不硬编码 `userId === 1`。
- 修改部门后说明岗位变化；角色数据范围受部门影响时提示权限可能变化。
- 关闭含未保存修改的抽屉前进行确认。
- 提交失败后保留输入并把字段错误定位到对应控件。

## 13. 角色授权

角色授权单独使用 `USER-005` 流程，不和普通资料更新共享提交按钮。

### 13.1 授权抽屉

- 顶部显示用户昵称、账号和当前部门。
- 角色列表支持名称搜索和已选过滤。
- 每个角色显示名称、编码、状态和简短数据范围摘要。
- 不可分配但已持有的角色只读展示，并说明原因。
- 操作者不能分配自己无权管理的角色。

### 13.2 保存确认

当新增或移除高风险角色时，保存前显示变更摘要：

```text
将为“陈晨”新增 1 个角色，移除 2 个角色
+ 企业管理员
- 访客
- 数据查看员
```

后端在同一事务中更新 `UserRole`，写入权限变更审计，并按约定刷新权限缓存或失效会话。前端成功后重新获取用户权限摘要，不在本地猜测最终权限。

## 14. 状态、安全与删除

### 14.1 启用和停用

停用确认文案：

```text
停用“{昵称}（{账号}）”后，该用户将无法继续登录。
当前在线会话将按系统安全策略失效。
```

规则：

- 禁止停用当前登录账号。
- 禁止停用受保护超级管理员。
- 是否允许停用最后一个企业管理员由后端校验。
- 停用不删除角色、岗位和部门关联，重新启用后恢复原有关联。
- 状态修改成功后刷新当前行；失败时不做乐观状态反转动画。

### 14.2 重置密码

重置方式：

- 服务端生成临时密码，优先。
- 管理员手动设置，作为兼容方案。
- 发送设置密码链接，在通知能力具备后启用。

弹窗必须说明是否会退出在线设备、是否要求首次登录改密。成功后使用专门结果区域显示一次性临时密码，不把密码放入 Toast、URL、埋点或操作日志。

### 14.3 删除

删除确认文案：

```text
删除“{昵称}（{账号}）”后，该账号将无法登录，现有会话会失效。
历史审计记录仍会保留。此操作不能在页面中撤销。
```

删除规则：

- 禁止删除当前登录账号和受保护超级管理员。
- 后端在一个事务中逻辑删除用户、归档账号名并处理 `UserRole`、`UserPost` 关联。
- 删除后失效该用户全部在线会话并刷新权限缓存。
- 删除不物理清理历史登录日志和操作日志。
- 首期不提供批量删除，避免部分成功和关联数据处理不清晰。

## 15. 批量、导入与导出

### 15.1 首期批量操作

首期仅建议支持：

- 批量启用。
- 批量停用。
- 批量调整部门（业务确认后）。

批量确认必须显示目标数量和部门范围。结果允许部分成功时，返回：

- 成功数量。
- 失败数量。
- 每条失败的用户识别信息和稳定错误码。
- 可下载失败明细。

### 15.2 导入

导入分为四步：

```text
下载模板 → 上传并预检 → 确认导入策略 → 查看结果
```

- 上传后先预检，不直接写库。
- 明确“只新增”和“更新已有用户”的差异。
- 更新匹配规则必须固定为租户内账号，不能用昵称匹配。
- 模板说明部门、岗位和角色的匹配方式。
- 错误结果不能用未经清理的 HTML 字符串直接渲染。
- 导入量较大时使用异步任务并提供进度和结果下载。

### 15.3 导出

- 导出遵循当前查询条件、部门范围和数据权限。
- 导出前显示预计范围，不默认导出整个租户。
- 手机、邮箱和登录 IP 按权限脱敏。
- 大数据量导出转为异步任务。

导入导出依赖后端文件与任务能力，不纳入第一开发切片。

## 16. 业务规则

### 16.1 查询

后端必须同时应用：

1. 当前租户条件。
2. `del_flag` 未删除条件。
3. 当前操作者的数据范围。
4. 部门与是否包含下级的条件。
5. 关键词、状态、角色和时间条件。
6. 稳定排序与分页。

默认排序建议为创建时间倒序、用户 ID 倒序。客户端不得传入任意数据库字段作为排序表达式。

### 16.2 新增

后端必须校验：

1. 操作者有新增用户权限。
2. 租户人数上限未超出。
3. 账号格式合法，且租户内未被未删除用户占用。
4. 账号不包含归档分隔符。
5. 部门属于当前租户、状态正常且操作者有权分配。
6. 岗位和角色属于当前租户、状态可用且操作者有权分配。
7. 密码由用户用例统一哈希，明文不进入 Repository、日志或响应。
8. 用户、`UserPost` 和 `UserRole` 在同一事务中写入。

### 16.3 编辑与授权

- 基础资料更新、组织关系更新和角色授权使用清晰的事务边界。
- 邮箱或手机号影响验证码登录时，重复值策略必须先明确。
- 并发编辑应使用更新时间或版本字段检测冲突，避免后提交者静默覆盖。
- 角色授权接口根据服务端当前状态计算变更，不信任前端提供的旧角色列表。
- 权限变化何时影响已登录会话必须形成统一策略。

## 17. 权限设计

建议权限点：

| 权限                       | 用途                     |
| -------------------------- | ------------------------ |
| `system:user:list`         | 查看用户列表             |
| `system:user:query`        | 查看用户详情和选项       |
| `system:user:add`          | 新增用户                 |
| `system:user:edit`         | 编辑基础资料、部门和岗位 |
| `system:user:changeStatus` | 启用和停用用户           |
| `system:user:authRole`     | 分配角色                 |
| `system:user:resetPwd`     | 重置他人密码             |
| `system:user:remove`       | 删除用户                 |
| `system:user:import`       | 导入用户                 |
| `system:user:export`       | 导出用户                 |

权限规则：

- 没有页面权限时返回 403，不以空表格代替。
- 没有某项操作权限时隐藏操作；对象规则不允许时可以禁用并说明原因。
- 按钮显隐不是安全边界，所有操作由后端重复校验。
- `system:user:edit` 不隐含角色授权和密码重置权限。
- 超级管理员能力不能成为普通角色设计的默认前提。

## 18. 接口建议

### 18.1 用户列表

```http
GET /api/v1/system/users
```

查询参数：

```text
page=1
pageSize=20
keyword=
deptId=
includeChildren=true
status=
roleId=
createdFrom=
createdTo=
```

响应只返回列表需要的摘要字段，不返回密码哈希、全部角色详情或无权限的联系方式。

### 18.2 用户详情与选项

```http
GET /api/v1/system/users/{userId}
GET /api/v1/system/users/options
GET /api/v1/system/users/{userId}/edit-options
```

- `options` 返回创建所需的可选部门、岗位和角色，也可以拆成各模块独立选项接口。
- `edit-options` 保留用户已关联但当前停用的选项，并返回字段级能力，例如 `canChangeDept`、`canAuthorizeRole`。
- 前端不能通过用户 ID 推断受保护账号。

### 18.3 新增与编辑

```http
POST  /api/v1/system/users
PATCH /api/v1/system/users/{userId}
```

新增示例：

```json
{
  "username": "chenchen",
  "nickname": "陈晨",
  "passwordMode": "generated",
  "email": "chenchen@example.com",
  "phonenumber": "13800138000",
  "sex": "2",
  "deptId": 101,
  "postIds": [201],
  "roleIds": [301],
  "status": "0",
  "remark": "产品运营"
}
```

编辑接口不接收 `roleIds`、密码、租户、逻辑删除和审计字段。

### 18.4 角色、状态和密码

```http
PUT  /api/v1/system/users/{userId}/roles
PUT  /api/v1/system/users/{userId}/status
POST /api/v1/system/users/{userId}/password-reset
```

这些接口分别拥有独立权限、审计类型和会话处理策略。

### 18.5 删除

```http
DELETE /api/v1/system/users/{userId}
```

后端返回稳定错误码，例如：

- `USER_SELF_OPERATION_FORBIDDEN`
- `USER_PROTECTED`
- `LAST_ADMIN_FORBIDDEN`
- `DEPT_NOT_ASSIGNABLE`
- `ROLE_NOT_ASSIGNABLE`
- `USER_CONFLICT`

## 19. 数据状态

页面需要覆盖：

- 首次加载骨架屏。
- 部门树和用户列表分别加载。
- 后台刷新时保留现有数据并显示轻量刷新状态。
- 首次空用户状态。
- 查询无结果状态。
- 部门树加载失败但列表仍可使用的降级状态。
- 用户列表加载失败和重试。
- 选项局部加载失败和重试。
- 无页面权限。
- 对象被删除或失去数据权限。
- 保存中防重复提交。
- 并发修改冲突。
- 批量操作部分成功。
- 会话失效策略执行失败时的持续提醒。

刷新后尽量保留查询条件、部门选择、分页、列设置和滚动位置。

## 20. 无障碍与可用性

- 部门树可通过键盘展开、收起和选择。
- 收起部门栏后仍有带文字或可访问名称的恢复入口。
- 表格复选框的名称包含对应用户昵称和账号。
- 状态同时使用文字与状态标识，不只依赖红绿颜色。
- 抽屉打开后焦点进入标题或第一个错误字段，关闭后返回触发元素。
- 危险操作按钮使用明确动词，例如“停用用户”“删除用户”。
- 一次性临时密码区域对屏幕录制和肩窥风险提供提示，但不阻止密码管理器工作。
- 加载、筛选和保存过程中避免整个页面跳动。

## 21. 首期范围

### 21.1 包含

- 部门树筛选和包含下级选择。
- 用户关键词、状态和角色查询。
- 用户分页列表和列设置。
- 用户详情。
- 新增和编辑用户。
- 部门和岗位关联。
- 独立角色授权。
- 启用、停用、重置密码和逻辑删除。
- 租户、数据范围、对象能力和按钮权限校验。
- 状态变化、权限变化和删除后的会话联动。

### 21.2 暂不包含

- 用户头像管理。
- 批量删除。
- 跨租户移动用户。
- 用户合并。
- 自定义字段。
- 审批后生效的角色授权。
- 完整手机端管理体验。
- 导入导出和异步任务。
- 邀请链接与首次登录强制改密，直到后端具备真实能力。
- 在列表内嵌在线设备管理；通过用户详情跳转专门会话页面。

## 22. 开发切片

建议按依赖关系实施：

1. 只读切片：部门筛选、查询、分页、表格和详情。
2. 资料切片：新增、编辑、部门和岗位关联。
3. 授权切片：角色选项、角色变更摘要、权限缓存和审计。
4. 安全切片：启停、重置密码、删除和会话失效。
5. 批量与文件切片：批量操作、导入、导出和结果任务。

每个切片都需要后端用例、权限点、前端交互和审计结果同时成立，不能只完成页面外观。

## 23. 验收要点

1. 选择部门后能够明确切换是否包含下级部门。
2. 查询条件、分页和部门选择在详情返回后保持。
3. 列表和详情不返回或展示密码哈希、租户内部字段和逻辑删除字段。
4. 创建用户时账号唯一性、部门、岗位和角色都由后端再次校验。
5. 修改基础资料不会意外覆盖角色关联。
6. 当前账号和受保护账号不能被停用或删除。
7. 停用、删除、重置密码和角色变更按约定影响在线会话。
8. 临时密码只显示一次，不进入普通消息、URL、日志和埋点。
9. 批量操作能够返回部分失败明细。
10. 无权限、数据范围、对象已变化和并发冲突有不同反馈。
11. 页面在浅色、深色和紧凑布局下保持可读。
12. 键盘可完成查询、查看详情、编辑和确认操作。

## 24. 待跨模块确认

1. 邮箱和手机号是否要求租户内唯一；这会直接影响验证码登录的确定性。
2. 用户是否必须归属部门，还是允许“未分配部门”。
3. 岗位是否严格归属部门，部门变化时如何处理原岗位。
4. 创建用户必须至少分配一个角色，还是允许待授权账号。
5. 初始密码采用服务端生成、管理员设置还是邀请链接。
6. 是否增加首次登录强制改密字段和流程。
7. 停用、重置密码、角色变化和部门变化是否立即失效全部会话。
8. 如何判断“最后一个企业管理员”，以及哪些账号属于受保护账号。
9. 用户管理默认部门范围是全部可见数据还是当前部门及下级。
10. 数据范围变化后部门树、用户列表和角色权限缓存如何刷新。
11. 导入更新已有用户时允许覆盖哪些字段。
12. 登录 IP 的查看权限、脱敏规则和代理链展示方式。

这些结论确认后，需要同步到核心用户流程、角色管理、岗位管理、认证安全和接口文档。

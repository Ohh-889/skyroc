## 2. 已知事实

### 2.1 产品事实

- 部门管理用于查看和维护组织树。
- 页面需要支持新增、编辑、移动、停用、删除、查看成员和设置负责人。
- 用户归属部门。
- 角色数据范围包含本部门、本部门及下级部门和自定义部门。
- 当前应用尚未实现部门、用户和角色业务页面。

### 2.2 后端事实

当前 `Dept` 模型已经确定：

| 字段 | 含义 |
| --- | --- |
| `id` | 部门 ID |
| `parent_id` | 父部门 ID，顶级部门的父 ID 为 `0` |
| `ancestors` | 从虚拟根节点到父部门的 ID 路径 |
| `dept_name` | 部门名称，最长 30 个字符 |
| `dept_category` | 部门类别编码 |
| `order_num` | 同级显示顺序 |
| `leader` | 负责人用户 ID |
| `phone` | 联系电话，最长 11 个字符 |
| `email` | 联系邮箱，最长 50 个字符 |
| `status` | `0` 正常，`1` 停用 |
| `tenant_id` | 租户编号 |
| `del_flag` | 逻辑删除标志 |
| 审计字段 | 创建部门、创建人、更新人、创建时间和更新时间 |

树结构同时存储 `parent_id` 和 `ancestors`。两者必须由后端在同一个用例中保持一致，前端不能读取、编辑或提交 `ancestors`。

当前后端部门模块只有表结构、树实体规则和异常定义，尚无接口层、Repository 和 Service。移动部门时，模型方法只更新当前节点，完整用例仍需在事务中重算全部子孙的 `ancestors`。

## 3. 页面目标

页面需要让有权限的管理员：

1. 在一个页面内看清当前租户的组织层级和关键状态。
2. 快速新增顶级部门或当前部门的直接下级。
3. 编辑部门信息，并以明确方式移动部门。
4. 在修改状态或删除前理解影响范围。
5. 从部门进入对应的用户筛选结果，而不是维护第二套成员列表。
6. 无法操作时能够知道是权限、状态还是关联数据造成的限制。

## 4. 设计结论

部门管理采用：

```text
可折叠查询区
  + 树形表格
  + 新增/编辑抽屉
  + 高风险操作确认
```

不采用左侧组织树和右侧详情的双栏布局。当前主要任务是维护组织结构，字段量有限，树形表格能够在同一阅读路径中呈现层级、负责人、排序、状态和操作。

不使用拖拽移动和拖拽排序。拖拽难以明确区分“更换上级”和“同级排序”，容易误操作，键盘和窄屏体验也较差。移动通过编辑抽屉中的“上级部门”完成。

首期不提供批量删除。部门存在上下级、用户、岗位、角色数据范围等引用，批量删除容易产生难以解释的部分成功结果。

```text
├──────────────────────────────────────────────────────────────────────────┤
│ 组织架构                         [新增顶级部门] [全部展开] [刷新] [列设置] │

│ 部门名称       类别      负责人    联系电话    排序   状态    操作        │

│   ├ 产品中心   中心      陈晨      137****    10     正常    新增下级…  │
│   │ ├ 产品部   部门      周宁      136****    10     正常    新增下级…  │

```

- 页面容器复用现有后台布局。
- 查询区和表格区使用独立卡片。
- 树形主列左对齐，其余信息按内容对齐。
- 操作列固定在右侧。
- 默认展开前两级；保留用户在当前页面会话中的展开状态。
- 表格不分页。

### 6.2 窄屏

- 页面允许横向滚动，不强行把树表格改成卡片列表。
- 默认只显示部门名称、负责人、状态和操作。
- 创建时间、联系电话和类别进入列设置。
- 编辑抽屉占满可用宽度。
- 行操作收进“更多”菜单，保留一个最常用的“编辑”入口。

## 7. 查询设计

### 7.1 查询字段

| 字段 | 控件 | 规则 |
| --- | --- | --- |
| 部门名称 | 输入框 | 去除首尾空格，模糊匹配 |
| 状态 | 单选下拉 | 全部、正常、停用 |
| 部门类别 | 单选下拉 | 仅在类别字典明确后展示 |

首期不提供创建时间查询。部门管理的主要任务是组织维护，而不是按时间审计；创建时间可作为表格辅助列。

### 7.2 树搜索结果

查询结果必须包含：

- 命中的部门。
- 命中部门的全部祖先节点。
- 命中节点原有的层级关系。

命中行使用轻量文字高亮，祖先路径仅用于提供上下文，不应被错误标记为命中。

无结果时展示：

```text
没有找到符合条件的部门
尝试调整部门名称、状态或类别
```

## 8. 树形表格

### 8.1 列定义

| 列 | 默认显示 | 说明 |
| --- | --- | --- |
| 部门名称 | 是 | 树形主列，名称旁可显示停用提示 |
| 部门类别 | 是 | 显示字典名称，不展示原始编码 |
| 负责人 | 是 | 展示姓名，空值显示“未设置” |
| 联系电话 | 是 | 无值显示 `—` |
| 排序 | 是 | 展示同级排序值 |
| 状态 | 是 | 正常使用绿色，停用使用中性或橙色 |
| 创建时间 | 否 | 通过列设置开启 |
| 操作 | 是 | 固定右侧 |

首期不展示成员数量，避免列表逐行统计和额外聚合请求。

### 8.2 行操作

| 操作 | 条件 | 结果 |
| --- | --- | --- |
| 新增下级 | 当前部门正常且有新增权限 | 打开新增抽屉并预选当前部门 |
| 编辑 | 有编辑权限 | 打开编辑抽屉 |
| 查看成员 | 有用户查询权限 | 跳转用户管理并携带 `deptId` |
| 删除 | 有删除权限 | 执行删除前检查并显示确认 |

查看成员跳转：

```text
/system/users?deptId={deptId}
```

用户管理负责分页、用户状态、编辑等能力。是否包含下级部门由用户在用户管理页面主动选择。

## 9. 新增与编辑抽屉

### 9.1 字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 上级部门 | 是 | 顶级部门使用虚拟根节点 `0` |
| 部门名称 | 是 | 最长 30 个字符，同一上级下不可重名 |
| 部门类别 | 否 | 使用真实字典；字典未定义时隐藏 |
| 显示顺序 | 是 | 非负整数，默认 `0` |
| 负责人 | 否 | 当前租户可选用户 |
| 联系电话 | 否 | 最长 11 个字符 |
| 邮箱 | 否 | 合法邮箱，最长 50 个字符 |
| 状态 | 是 | 正常或停用 |

负责人选项展示：

```text
用户姓名 · 用户账号 · 当前所属部门
```

只显示当前租户内允许选择的用户。前端不通过已加载部门成员推断负责人候选范围。

### 9.2 新增顶级部门

- 上级部门默认显示“顶级部门”。
- 请求中提交 `parentId: 0`。
- 当前模型允许同一租户存在多个顶级部门，不在页面层假设固定公司根节点。

### 9.3 新增下级部门

- 上级部门默认选择触发行的部门。
- 保留修改上级部门的能力。
- 停用部门不能作为新部门的上级。

### 9.4 编辑和移动

- 修改“上级部门”即代表移动当前部门。
- 上级部门选择器排除当前部门及其全部子孙。
- 如果当前部门存在下级，改变上级时在字段下方提示：

```text
移动后，该部门及其全部下级将一起迁移，成员归属不变。
```

- 保存前不要求二次弹窗，后端冲突或数据已变化时显示明确错误。

## 10. 业务规则

### 10.1 新增

后端必须校验：

1. 当前租户上下文存在。
2. 上级部门属于当前租户、未删除且状态正常。
3. 同一上级下不存在同名的未删除部门。
4. 当前用户有权在目标上级部门下新增。
5. `parent_id` 和 `ancestors` 由后端统一生成。

### 10.2 移动

移动必须在一个事务中完成：

1. 查询并校验当前部门和目标上级部门。
2. 校验目标上级不等于当前部门。
3. 校验目标上级不属于当前部门的子树。
4. 校验操作者对原部门和目标上级均具有操作权限。
5. 更新当前部门的 `parent_id` 和 `ancestors`。
6. 重算全部子孙的 `ancestors`。
7. 刷新部门树和数据权限相关缓存。

任一步失败都必须整体回滚。

### 10.3 停用与启用

建议规则：

- 存在正常子部门时禁止停用。
- 当前部门存在有效用户时禁止停用。
- 停用不自动级联子部门。
- 启用部门前要求全部上级部门均为正常状态。
- 不因为启用一个子部门而隐式启用全部祖先。
- 停用部门不能作为新建或移动操作的目标上级。

后端返回失败时，应携带稳定错误码和可直接展示的用户文案。

### 10.4 删除

只允许删除同时满足以下条件的部门：

- 没有直接或间接下级部门。
- 没有关联用户。
- 没有关联岗位。
- 不是受保护的默认部门。
- 操作者拥有该部门的数据权限。

如果部门被角色自定义数据范围引用，删除确认必须展示影响；删除用例需要在同一事务中清理 `sys_role_dept` 关联，并刷新相关角色的数据权限缓存。

删除采用逻辑删除。确认文案：

```text
删除“{部门名称}”后将不能继续分配用户，历史审计记录仍会保留。
```

## 11. 权限设计

建议权限点：

| 权限 | 用途 |
| --- | --- |
| `system:dept:list` | 查看部门列表 |
| `system:dept:query` | 查看部门详情和选项 |
| `system:dept:add` | 新增顶级或下级部门 |
| `system:dept:edit` | 编辑、移动、启用和停用 |
| `system:dept:remove` | 删除部门 |
| `system:user:list` | 从部门进入成员列表 |

没有某项权限时隐藏对应操作；不能只依靠前端隐藏，后端必须重复校验。

非超级管理员只能看见其数据范围允许访问的部门。服务端返回的可见节点需要包含构建树所需的祖先上下文，但祖先上下文不因此获得编辑权限。

## 12. 接口建议

### 12.1 部门列表

```http
GET /api/v1/system/depts?deptName=&status=&deptCategory=
```

建议返回当前租户和当前数据范围内的平铺数组，由前端根据 `id` 和 `parentId` 构树。列表无需返回 `ancestors`。

### 12.2 部门详情

```http
GET /api/v1/system/depts/{deptId}
```

详情返回 `parentName`、`leaderName` 等展示字段。

### 12.3 新增、编辑和删除

```http
POST   /api/v1/system/depts
PUT    /api/v1/system/depts/{deptId}
DELETE /api/v1/system/depts/{deptId}
```

新增和编辑请求字段：

```json
{
  "parentId": 100,
  "deptName": "产品部",
  "deptCategory": "department",
  "orderNum": 10,
  "leader": 10001,
  "phone": "13800138000",
  "email": "product@example.com",
  "status": "0"
}
```

禁止接收 `ancestors`、`tenantId`、`delFlag` 和审计字段。

### 12.4 部门选项

```http
GET /api/v1/system/depts/options
GET /api/v1/system/depts/options?excludeSubtreeOf={deptId}
```

第二个接口用于编辑部门时选择新上级，服务端直接排除当前部门和整棵子树。

## 13. 数据状态

页面需要覆盖：

- 首次加载骨架屏。
- 后台刷新，保留已有表格并显示轻量刷新状态。
- 空租户组织状态，引导新增第一个顶级部门。
- 查询无结果状态。
- 接口错误和重试。
- 权限不足。
- 数据被其他管理员修改后的冲突。
- 保存中防重复提交。
- 删除或停用校验失败。

刷新数据后尽量保留当前查询条件、展开节点和滚动位置。

## 14. 无障碍与可用性

- 树节点展开按钮必须可通过键盘操作，并提供明确的可访问名称。
- 状态不能只依赖颜色表达，必须同时展示文字。
- 抽屉打开后焦点进入标题或第一个字段，关闭后返回触发按钮。
- 所有图标按钮提供 `aria-label` 或可见提示。
- 危险操作确认按钮使用明确动词，例如“删除部门”，不只写“确定”。
- 搜索、展开、刷新和保存过程中避免页面整体跳动。

## 15. 首期范围

### 15.1 包含

- 部门树查询和展示。
- 部门名称和状态查询。
- 新增顶级部门和下级部门。
- 编辑部门。
- 通过更换上级移动部门。
- 启用、停用和删除。
- 设置负责人和联系方式。
- 跳转用户管理查看成员。
- 权限、租户、逻辑删除和数据范围校验。

### 15.2 暂不包含

- 拖拽移动和排序。
- 批量删除。
- 组织架构关系图。
- 部门成员内嵌列表。
- 成员数量实时统计。
- 部门合并和拆分。
- 部门导入导出。
- 历史组织版本和定时生效。
- 跨租户移动。

## 16. 待跨模块确认

以下事项会影响用户、角色、岗位和权限，需要实现前确认：

1. 是否存在固定且不可删除的默认部门 ID。
2. 部门类别字典的真实来源和允许值。
3. 岗位是否必须归属部门，以及删除部门时的约束。
4. 删除被角色自定义数据范围引用的部门时，是阻止删除还是确认后清理关联。
5. 数据范围受限用户是否能够把部门移动到另一个可见分支。
6. 用户管理“包含下级部门”筛选的接口字段。
7. 部门树和角色数据权限的缓存策略。

这些结论确认后，需要同步到角色权限、用户管理、岗位管理和接口文档。

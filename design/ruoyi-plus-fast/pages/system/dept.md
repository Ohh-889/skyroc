## 2. 架构结论

部门管理不是一张可以随意增删的基础表，而是用户归属、岗位归属、角色数据范围和组织树查询共同依赖的组织主数据入口：

```text
组织树维护
  → 用户与负责人归属
  → 岗位和角色数据范围引用
  → 登录会话中的部门展示信息
  → 查询权限、缓存和操作审计
```

页面职责：

- 前端负责树形展示、条件查询、表单交互、权限显隐、危险操作确认和结果反馈。
- 部门管理用例负责租户隔离、数据范围、同级名称唯一性、树结构一致性和事务边界。
- 用户模块负责返回可选负责人和按部门筛选用户，不由部门页面复制用户查询逻辑。
- 岗位与角色模块负责部门引用关系；停用和删除前由后端统一校验。
- 数据权限模块负责组织变更后的缓存失效，前端不自行展开整棵树计算授权范围。
- 操作日志记录新增、编辑、移动、停用和删除，不在页面请求中提交操作者或审计字段。

页面采用：

```text
查询区 + 树形表格
  + 新增/编辑抽屉
  + 删除确认弹窗
```

树形表格承担主要浏览和操作任务。新增、编辑和移动在右侧抽屉完成，保留当前组织上下文；删除使用独立确认弹窗，并在执行前展示后端约束结果。

## 3. 已知事实与设计假设

### 3.1 RuoYi 前端事实

参考页面已经包含：

- 按部门名称、类别编码和状态查询。
- 树形表格展示部门名称、类别编码、排序、状态和创建时间。
- 新增部门、编辑部门、删除部门和展开/折叠全部。
- 新增时加载完整部门列表作为上级选项。
- 编辑时使用 `/list/exclude/{deptId}` 排除当前部门及其全部子孙。
- 表单字段包括上级部门、部门名称、类别编码、显示顺序、负责人、联系电话、邮箱和状态。
- 编辑时通过 `/system/user/list/dept/{deptId}` 获取负责人候选用户。
- 列表由平铺部门数据在前端构造成树，不分页。

参考页面是业务覆盖面的依据，不要求复制 Element Plus 的视觉样式或 600px 居中弹窗。

### 3.2 RuoYi 控制器事实

`SysDeptController` 已明确以下契约和约束：

| 能力         | 方法与路径                               | 权限                 |
| ------------ | ---------------------------------------- | -------------------- |
| 部门列表     | `GET /system/dept/list`                  | `system:dept:list`   |
| 排除当前子树 | `GET /system/dept/list/exclude/{deptId}` | `system:dept:list`   |
| 部门详情     | `GET /system/dept/{deptId}`              | `system:dept:query`  |
| 新增部门     | `POST /system/dept`                      | `system:dept:add`    |
| 修改部门     | `PUT /system/dept`                       | `system:dept:edit`   |
| 删除部门     | `DELETE /system/dept/{deptId}`           | `system:dept:remove` |
| 部门选项     | `GET /system/dept/optionselect`          | `system:dept:query`  |

控制器还明确：

- 新增和修改都校验部门名称唯一性。
- 上级部门不能是当前部门自己。
- 停用部门前必须保证没有正常子部门，且当前部门没有已分配用户。
- 默认部门不允许删除。
- 存在下级部门、用户或岗位时不允许删除。
- 查询详情、修改和删除前校验部门数据范围。
- 新增和修改启用重复提交保护并记录操作日志。

### 3.3 当前 FastAPI 事实

当前 `skroc-fast` 已有：

- `sys_dept` 模型和租户隔离字段。
- `parent_id` 与 `ancestors` 双重树结构，根节点 `parent_id = 0`、`ancestors = "0"`。
- 部门名称、类别编码、排序、负责人、联系电话、邮箱和状态字段。
- `Dept.attach_to()` 循环层级防护。
- `GET /api/v1/system/dept/deptTree`，供用户管理加载部门选择树。
- 部门树按租户、名称、类别、状态、创建时间和归属子树筛选。

当前尚未具备：

- 部门管理列表、详情、新增、修改、排除子树、删除和选项接口。
- 移动部门时整棵子树 `ancestors` 的事务性重算。
- RuoYi 的 `system:dept:*` 权限门禁；现有部门树暂由超级管理员门禁代管。
- 停用、删除、用户、岗位和角色数据范围引用的完整校验链。

因此 HTML 是交互设计原型，不能描述为已对接 CRUD。

### 3.4 设计假设

- 首期沿用 RuoYi 字段和单数接口路径，避免再维护一套复数 REST 契约。
- `deptCategory` 目前没有已验证的字典来源，查询和表单先使用文本编码输入；以后有字典再替换为可搜索选择器。
- 列表主列优先展示组织层级；负责人和联系电话作为业务增强列，创建时间可通过列设置显示。
- 首期使用数字排序，不做拖拽移动或拖拽排序。
- “查看成员”复用 `/system/user?deptId={deptId}`，不在部门页嵌入第二套成员表格。
- 状态不使用行内开关，避免一次误触立即影响用户归属和数据范围。
- 新增和编辑采用抽屉；这是本项目交互选择，不改变后端契约。

## 4. 页面目标

页面需要让有权限的管理员：

1. 快速看清当前租户的组织层级、负责人、排序和状态。
2. 通过名称、类别编码和状态定位部门，同时保留命中节点的祖先上下文。
3. 新增顶级部门或当前节点的直接下级。
4. 编辑部门信息，并通过更换上级部门完成受控移动。
5. 在停用或删除前理解子部门、用户、岗位和默认部门约束。
6. 从部门直接进入用户管理的对应筛选结果。
7. 在权限不足、重复名称、循环层级或并发变化时得到可执行反馈。

- 使用页面全部可用宽度，内容区最大宽度与菜单管理保持一致。
- 页面内边距 24px；紧凑模式使用 16px。
- 查询区和表格区使用两个弱边框容器，不叠加强阴影。
- 部门名称列固定左侧，操作列固定右侧；表格允许横向滚动。
- 表格不分页，底部展示当前可见节点数量和刷新时间。
- 每级缩进 24px，展开控件、部门图标和名称保持稳定对齐。
- 行操作直接显示“新增下级”和“编辑”，成员与删除在宽度不足时进入更多菜单。

### 6.2 中等宽度

- `992px - 1199px` 隐藏联系电话，负责人保留。
- 类别编码与排序维持独立列，创建时间默认不显示。
- 工具栏按钮收缩为图标加 Tooltip。
- 操作列固定右侧，低频操作进入更多菜单。

### 6.3 窄屏

- `< 768px` 保证查询、展开树、查看状态和编辑入口可用。
- 表格最小宽度 920px，容器横向滚动，不把树结构拆成失去层级关系的卡片流。
- 新增/编辑抽屉占满屏幕，字段改为单列，底部操作固定。
- 删除仍需明确确认，不因窄屏降低风险提示。

## 7. 查询设计

### 7.1 查询字段

| 字段     | 控件       | 请求字段       | 规则                                  |
| -------- | ---------- | -------------- | ------------------------------------- |
| 部门名称 | 文本输入框 | `deptName`     | 去除首尾空格，模糊匹配，最多 30 字符  |
| 类别编码 | 文本输入框 | `deptCategory` | 去除首尾空格，模糊匹配，最多 100 字符 |
| 状态     | 单选下拉   | `status`       | 全部、正常 `0`、停用 `1`              |

交互规则：

- 点击查询或在文本输入框按 Enter 执行请求。
- 修改条件不自动请求，避免树频繁重构和展开状态抖动。
- 重置清空全部条件、清除校验提示并重新加载完整树。
- 查询状态写入 URL 查询参数，刷新或返回页面后可以恢复。

### 7.2 树搜索语义

- 命中子节点时必须保留其祖先路径，否则用户无法判断组织归属。
- 祖先路径节点仅用于上下文，不算作真实命中结果。
- 查询后自动展开到全部命中节点。
- 清空条件后恢复查询前的展开状态。
- 命中文字轻量高亮，不能只依靠行背景表达命中。
- 无结果时显示“没有找到符合条件的部门”，并提供重置入口。

## 8. 树形表格

### 8.1 列定义

| 列       | 展示规则                                        | 默认显示 |
| -------- | ----------------------------------------------- | -------- |
| 部门名称 | 展开控件、部门图标、名称；超长省略并 Tooltip    | 是       |
| 类别编码 | 原始 `deptCategory`；空值显示 `—`               | 是       |
| 负责人   | 优先显示负责人姓名；无法解析时显示“未设置”      | 是       |
| 联系电话 | 默认脱敏；无值显示 `—`                          | 是       |
| 排序     | 显示 `orderNum`，同级按排序值和部门 ID 稳定排序 | 是       |
| 状态     | 正常、停用，使用文字和状态色                    | 是       |
| 创建时间 | `YYYY-MM-DD HH:mm`                              | 否       |
| 操作     | 新增下级、编辑、成员、删除                      | 是       |

负责人姓名和脱敏电话属于本设计相对 RuoYi 列表的增强。如果管理列表接口只返回负责人 ID，前端不得逐行请求用户详情；应由列表 VO 一次返回 `leaderName`，或者暂时隐藏负责人列。

### 8.2 展开策略

- 首次进入默认展开前两级，兼顾结构感知和页面密度。
- 用户可以逐节点展开，也可以一键展开或收起全部。
- 刷新、查询、编辑成功后尽量保留当前展开节点和滚动位置。
- 新增子部门成功后展开父节点并定位新增行。
- 删除最后一个子部门后同步移除父节点展开控件。
- 大数据量若改为服务端懒加载，单节点失败只在对应节点下显示重试，不清空全表。

### 8.3 状态表达

- 正常使用绿色标签，停用使用橙色标签，并始终显示文字。
- 停用部门保留完整可读性，不将整行降到不可辨认。
- 停用部门不能新增下级，按钮显示禁用原因；编辑、查看成员和删除仍按权限与业务约束决定。

## 9. 工具栏与操作

### 9.1 页面级操作

| 操作                | 权限               | 行为                                 |
| ------------------- | ------------------ | ------------------------------------ |
| 新增顶级部门        | `system:dept:add`  | 打开新增抽屉，上级部门为“顶级部门”   |
| 展开全部 / 收起全部 | `system:dept:list` | 切换当前已加载树的展开状态           |
| 刷新                | `system:dept:list` | 保留查询条件并重新加载               |
| 列设置              | `system:dept:list` | 控制负责人、电话、创建时间等非关键列 |

部门名称、状态和操作列不可隐藏。

### 9.2 行操作

| 操作     | 权限                 | 行为                                           |
| -------- | -------------------- | ---------------------------------------------- |
| 新增下级 | `system:dept:add`    | 预填当前行作为上级部门                         |
| 编辑     | `system:dept:edit`   | 拉取详情和排除子树后的上级选项，再打开抽屉     |
| 查看成员 | `system:user:list`   | 跳转 `/system/user?deptId={deptId}`            |
| 删除     | `system:dept:remove` | 显示确认后调用删除接口，由后端执行完整约束校验 |

- 没有权限的操作不展示。
- 因部门状态或节点规则不可用的操作保留禁用态和 Tooltip。
- 页面不使用行内状态开关；状态在编辑抽屉中修改。
- 删除不做前端乐观更新，成功后再移除节点。

## 10. 新增与编辑抽屉

### 10.1 抽屉结构

```text
新增 / 编辑部门
├── 组织归属
│   └── 上级部门
├── 基础信息
│   ├── 部门名称
│   ├── 类别编码
│   └── 显示顺序
├── 负责人和联系方式
│   ├── 负责人
│   ├── 联系电话
│   └── 邮箱
└── 部门状态
```

- 桌面端宽度 520px；窄屏占满。
- 打开时先展示骨架或加载状态，不能用上一条记录残留数据。
- 底部固定“取消”和“保存部门”。
- 保存中禁用重复提交，成功后关闭抽屉并定位更新节点。

### 10.2 字段规则

| 字段     | 必填 | 规则                                                     |
| -------- | ---- | -------------------------------------------------------- |
| 上级部门 | 是   | 顶级部门提交 `parentId: 0`；编辑时排除当前部门和全部子孙 |
| 部门名称 | 是   | 最长 30 字符，去除首尾空格，同一上级下不可重名           |
| 类别编码 | 否   | 最长 100 字符；当前无字典，不伪造固定枚举                |
| 显示顺序 | 是   | 非负整数，默认 `0`                                       |
| 负责人   | 否   | 从允许选择的租户用户中选择，提交用户 ID                  |
| 联系电话 | 否   | 中国大陆手机号规则，最长 11 位                           |
| 邮箱     | 否   | 合法邮箱，最长 50 字符                                   |
| 状态     | 是   | 正常 `0` 或停用 `1`                                      |

前端禁止提交 `ancestors`、`tenantId`、`delFlag` 和审计字段。

### 10.3 上级部门选择

- 新增顶级部门默认选择虚拟根节点“顶级部门”。
- 从行内“新增下级”进入时默认选择当前部门。
- 编辑时调用排除子树接口，避免选择自己或自己的下级。
- 停用部门显示但不可作为新建或移动目标，并解释禁用原因。
- 若当前部门有下级且上级发生变化，显示：

```text
移动后，该部门及其全部下级将一起迁移，成员归属不变。
```

### 10.4 负责人选择

- 候选项展示“姓名 · 账号 · 当前部门”。
- 参考实现编辑时只查询当前部门用户；本项目最终候选范围应由业务确认，不能由已加载表格行推断。
- 负责人不在候选范围或已停用时，编辑详情仍应显示原值和不可选原因，避免保存时静默清空。
- 列表和详情返回负责人姓名，提交只发送负责人用户 ID。

## 11. 业务规则

### 11.1 树结构

- 根部门的 `parentId` 为 `0`，不是 `null`。
- `parentId` 与 `ancestors` 必须由后端在同一事务中维护。
- 前端不读取、拼装或提交 `ancestors`。
- 同级按 `orderNum` 升序、部门 ID 升序稳定排序。
- 目标上级不能是当前部门或当前部门的任意子孙。
- 跨租户移动永远不允许。

### 11.2 新增

后端必须校验：

1. 当前租户和操作者有效。
2. 目标上级属于当前租户、未删除、状态正常且在数据范围内。
3. 同一上级下不存在同名的未删除部门。
4. 操作者具备 `system:dept:add`。
5. `parentId` 和 `ancestors` 由后端统一生成。

### 11.3 编辑与移动

移动必须在一个事务中完成：

1. 锁定或以可检测并发变化的方式读取当前部门与目标上级。
2. 校验原部门和目标上级的数据范围。
3. 校验目标上级不属于当前部门子树。
4. 更新当前部门 `parentId` 与 `ancestors`。
5. 重算全部子孙的 `ancestors`。
6. 刷新部门树、用户查询和数据权限相关缓存。
7. 写入操作日志。

任一步失败都整体回滚。

### 11.4 停用与启用

对齐 RuoYi 首期规则：

- 存在正常子部门时禁止停用。
- 当前部门存在已分配用户时禁止停用。
- 停用不自动级联子部门。
- 停用部门不能作为新部门或移动操作的目标上级。
- 启用前校验全部上级部门为正常状态。

失败时后端返回稳定错误码和可直接展示的中文文案；前端不根据缓存数据自行放行。

### 11.5 删除

只允许删除同时满足以下条件的部门：

- 不是受保护的默认部门。
- 不存在任何下级部门。
- 不存在关联用户。
- 不存在关联岗位。
- 操作者拥有 `system:dept:remove` 和该部门数据权限。

角色自定义数据范围对部门的引用处理仍需确认。删除确认文案：

```text
删除“{部门名称}”后将不能继续分配用户，历史审计记录仍会保留。
```

如果前端已知存在下级，只提示“存在下级部门，不能删除”，不提供伪装成可执行的危险按钮；最终结果仍以后端校验为准。

## 12. 权限设计

| 权限                 | 页面用途                         |
| -------------------- | -------------------------------- |
| `system:dept:list`   | 查看部门列表和刷新组织树         |
| `system:dept:query`  | 查看详情和部门选项               |
| `system:dept:add`    | 新增顶级或下级部门               |
| `system:dept:edit`   | 编辑、移动、启用和停用           |
| `system:dept:remove` | 删除部门                         |
| `system:user:list`   | 查看部门成员和加载允许的用户信息 |

- 前端权限只控制展示和可操作状态，不能替代后端鉴权。
- 非超级管理员只看见数据范围允许的部门。
- 为构建树而返回的只读祖先节点不能因此获得编辑权限。
- 接口权限失败时保留页面结构，并在对应区域展示无权限状态。

## 13. 接口契约

### 13.1 当前已实现接口

```http
GET /api/v1/system/dept/deptTree
```

用途：用户管理的部门筛选树，不足以支撑部门管理 CRUD。

支持的查询字段包括：

```text
deptId
parentId
deptName
deptCategory
status
belongDeptId
params[beginTime]
params[endTime]
```

响应节点：

```json
{
  "id": "100",
  "parentId": "0",
  "label": "Skyroc 集团",
  "weight": 0,
  "disabled": false,
  "children": []
}
```

该响应缺少负责人、电话、创建时间等管理字段，不能直接复用为管理表格数据源。

### 13.2 待实现的管理接口

保留 RuoYi 路径与业务语义，并由应用统一添加 `/api/v1` 前缀：

```http
GET    /api/v1/system/dept/list
GET    /api/v1/system/dept/list/exclude/{deptId}
GET    /api/v1/system/dept/{deptId}
POST   /api/v1/system/dept
PUT    /api/v1/system/dept
DELETE /api/v1/system/dept/{deptId}
GET    /api/v1/system/dept/optionselect
```

列表查询：

```http
GET /api/v1/system/dept/list?deptName=&deptCategory=&status=
```

响应使用本项目业务包络：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": [
    {
      "deptId": "100",
      "parentId": "0",
      "deptName": "Skyroc 集团",
      "deptCategory": "HQ",
      "orderNum": 0,
      "leader": "1",
      "leaderName": "王敏",
      "phone": "13800138000",
      "email": "admin@example.com",
      "status": "0",
      "createTime": "2026-08-05 09:30:00"
    }
  ]
}
```

- 大整数 ID 按项目序列化规则返回字符串，前端类型不能只写 `number`。
- 列表返回平铺数据，前端按 `deptId`、`parentId` 构树。
- 响应无需暴露 `ancestors`、`tenantId` 或 `delFlag`。

### 13.3 新增与修改请求

```json
{
  "deptId": "110",
  "parentId": "100",
  "deptName": "产品中心",
  "deptCategory": "CENTER",
  "orderNum": 10,
  "leader": "1024",
  "phone": "13800138000",
  "email": "product@example.com",
  "status": "0"
}
```

- 新增不提交 `deptId`，修改必须提交 `deptId`。
- `POST`、`PUT` 成功返回 `R[null]`；前端随后刷新列表，不假设响应携带完整实体。
- 重复提交、名称冲突、循环层级和引用约束使用不同错误码。

### 13.4 负责人候选

RuoYi 参考接口：

```http
GET /api/v1/system/user/list/dept/{deptId}
```

若本项目不采用“仅当前部门用户可成为负责人”的规则，应另行定义可搜索、分页的负责人选择接口，不能复用用户管理分页后在前端全量过滤。

## 14. 数据状态

### 14.1 首次加载

- 查询区可以立即交互。
- 表格显示保持树形层级的骨架行，避免页面高度跳变。
- 首次请求完成前禁用展开全部和刷新。

### 14.2 空状态

完整树为空：

```text
还没有部门
创建第一个顶级部门，开始搭建组织架构
[新增顶级部门]
```

查询无结果：

```text
没有找到符合条件的部门
尝试调整部门名称、类别编码或状态
[重置条件]
```

### 14.3 错误与冲突

- 列表失败：卡片内展示错误摘要和重试按钮，不让整页白屏。
- 详情失败：抽屉显示加载失败并允许重试，不打开空表单。
- 保存失败：保留用户输入，定位首个错误字段。
- 数据已变更：提示刷新最新数据后重试，不静默覆盖。
- 删除或停用受阻：直接展示后端返回的具体原因。

### 14.4 成功反馈

- 新增成功：“部门已新增”。
- 修改成功：“部门信息已更新”。
- 移动成功：“部门及其下级已移动”。
- 删除成功：“部门已删除”。
- 成功后刷新受影响分支，尽量保留查询、展开和滚动状态。

## 15. 无障碍与可用性

- 树节点展开按钮可通过键盘操作，并提供包含部门名称的可访问名称。
- 状态同时使用文字和颜色。
- 图标按钮提供 `aria-label` 和 Tooltip。
- 抽屉打开后焦点进入标题或首个字段，关闭后返回触发按钮。
- 删除确认按钮写“删除部门”，不只写“确定”。
- Escape 关闭当前最上层弹窗；保存中不允许关闭造成结果不明。
- 搜索、刷新和保存期间避免页面整体跳动。
- 联系电话默认脱敏，完整值是否可见由权限决定。

## 19. 待跨模块确认

1. 默认部门 ID 是否固定，以及租户初始化时如何创建。
2. `deptCategory` 是否接入真实字典，允许值和展示文案是什么。
3. 负责人候选是当前部门用户、当前子树用户，还是当前租户全部可见用户。
4. 岗位是否必须归属部门，以及删除时是否只阻止还是允许迁移后删除。
5. 部门被角色自定义数据范围引用时，是阻止删除还是事务内清理关联。
6. 移动部门后在线用户的数据范围缓存和会话信息何时刷新。
7. 用户管理是否需要显式 `includeChildren`，部门页“查看成员”默认是否包含下级。
8. 是否需要服务端树懒加载，以及切换阈值。

这些结论确认后，需要同步用户管理、岗位管理、角色权限和后端接口测试。

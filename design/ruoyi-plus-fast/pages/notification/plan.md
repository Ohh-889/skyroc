# 通知中心 PRD（提案）

> 文档状态：提案，待产品、后端和权限模型确认
>
> 适用范围：Skyroc Admin Web 管理后台，以及 `@skyroc/web-admin-notification` 通知基础组件

## 1. 产品定义

通知中心不是单纯的“铃铛下拉框”，而是一套面向后台任务、系统事件和业务协作的消息闭环：

```text
事件产生 → 规则判断 → 消息生成 → 按渠道投递 → 用户查看/处理 → 已读与回执 → 审计与统计
```

需要明确区分三类能力：

| 能力 | 解决的问题 | 典型内容 |
| --- | --- | --- |
| 实时提醒 | 用户现在是否需要注意 | 审批待办、失败告警、权限变更 |
| 通知中心 | 用户如何集中查看和处理消息 | 未读、筛选、详情、跳转、批量已读 |
| 通知管理 | 管理员如何配置和发布消息 | 公告、模板、受众、渠道、发送记录 |

## 2. 背景与现状

当前 `packages/web/admin-notification` 已提供运行时基础能力：

- 顶部通知按钮和下拉面板。
- 通知类型：`info`、`success`、`warning`、`error`、`message`。
- 未读计数、单条已读、全部已读、单条删除和清空。
- 优先级、浏览器原生通知、通知音效和免打扰时间段。
- 内存状态管理和演示数据。

当前缺口：

- 没有服务端持久化，刷新或换设备后状态丢失。
- 没有通知分类、筛选、搜索、详情和历史归档。
- 没有“待办”和“信息”两种处理语义的区分。
- 没有面向管理员的公告发布、模板、受众和发送记录。
- 没有实时订阅、幂等、重试、撤回和过期策略。
- 没有统一的通知权限、偏好和审计模型。

## 3. 产品目标

### 3.1 用户目标

1. 用户在 3 秒内知道是否有需要处理的事项。
2. 用户能够区分“需要行动”“仅供知悉”“系统告警”。
3. 用户可以从通知直接进入相关对象，并在完成任务后形成已处理回执。
4. 用户能够在通知中心找回近期历史消息，不依赖浏览器通知或重复询问他人。
5. 用户可以控制低价值提醒的渠道和免打扰时间，不错过高优先级安全消息。

### 3.2 管理目标

- 管理员可以向明确受众发布可追溯的公告。
- 业务系统可以通过统一事件契约发送消息，而不是各自实现弹窗和计数。
- 系统能够查询投递成功、失败、已读和处理情况。
- 高风险通知具备权限控制、审计记录和敏感信息保护。

### 3.3 非目标

- P0 不建设通用 IM、群聊、评论流或邮件营销平台。
- P0 不做复杂可视化编排和用户自定义规则引擎。
- P0 不保证所有通知都实时到达；实时性按类型定义 SLA。
- 不把公告、待办、操作反馈强行设计成同一种卡片。

## 4. 目标用户与场景

| 角色 | 高频场景 | 核心诉求 |
| --- | --- | --- |
| 普通员工 | 查看审批、任务和系统公告 | 少打扰、能直接处理 |
| 业务运营 | 跟进失败任务、异常数据和批处理结果 | 能定位对象、查看失败原因 |
| 系统管理员 | 发布公告、查看安全告警和权限变更 | 受众准确、可审计 |
| 审计/安全人员 | 查询高风险通知和处理回执 | 记录完整、不可抵赖 |

## 5. 信息架构

### 5.1 用户端入口

1. **顶部通知按钮**：显示未读数；只承载最近消息和快速处理。
2. **通知抽屉/中心页**：承载完整历史、筛选、搜索、批量操作和详情。
3. **业务对象详情**：通知点击后进入具体用户、审批、任务、日志或配置对象。
4. **个人通知设置**：管理用户可配置的渠道、分类和免打扰偏好。

建议路由：

```text
/notifications                 通知中心
/notifications/:notificationId 通知详情（可选，亦可使用抽屉）
/account/notification-settings 通知设置
```

### 5.2 管理端入口

```text
/system/notices                 公告列表
/system/notices/new             新建公告
/system/notices/:id/edit        编辑草稿
/system/notices/:id/recipients  受众与发送记录
/system/notification-templates  通知模板（P1）
/system/notification-deliveries 投递记录（P1）
```

公告管理和用户通知中心使用不同入口：前者是“发布与治理”，后者是“接收与处理”。

## 6. 通知分类与语义

### 6.1 一级分类

| 分类 | 是否需要行动 | 示例 | 默认优先级 |
| --- | --- | --- | --- |
| 待办任务 | 是 | 审批待处理、合同待确认 | high |
| 系统公告 | 否/视公告而定 | 维护、版本发布、制度通知 | normal |
| 业务消息 | 通常否 | 评论、提及、协作消息 | normal |
| 系统事件 | 通常否 | 导入完成、导出完成、同步完成 | low |
| 异常告警 | 通常是 | 任务失败、接口异常、数据风险 | high/urgent |
| 安全通知 | 是 | 异常登录、权限变化、密码修改 | high/urgent |

### 6.2 展示类型与业务分类分离

现有 `NotificationType` 继续作为视觉状态，不承担业务分类。建议新增：

```ts
category: 'task' | 'announcement' | 'message' | 'event' | 'alert' | 'security'
action?: {
  label: string;
  method?: 'navigate' | 'api';
  target?: string;
}
status: 'unread' | 'read' | 'processing' | 'resolved' | 'expired'
```

这样“导入成功”可以是 `type=success + category=event`，“权限被修改”可以是 `type=warning + category=security`。

## 7. P0 用户端功能

### 7.1 顶部快捷面板

- 展示最近 20 条，按服务端时间倒序。
- 显示未读数，超过 99 显示 `99+`。
- 支持全部已读、单条已读、删除本地记录。
- 未读消息使用背景和状态点双重表达，不能只依赖颜色。
- 点击消息：先标记已读，再按 `action` 跳转；跳转失败保留消息。
- 提供“查看全部”进入通知中心。
- 只在有未读或高优先级消息时使用轻量动效；尊重减少动效设置。

### 7.2 通知中心

- Tab：全部、待办、公告、消息、异常、安全。
- 筛选：已读状态、优先级、时间范围、来源模块。
- 搜索：标题、摘要和业务对象名称；服务端分页搜索。
- 批量操作：全部已读、标记已处理、删除已读。
- 列表项展示：分类、标题、摘要、来源、时间、优先级、状态。
- 详情展示：完整正文、发生时间、来源、关联对象、操作按钮、处理记录。
- 支持“仅看未读”和“仅看需要处理”。
- 空状态、无结果、加载失败、权限不足和消息已撤回需要分别设计。

### 7.3 待办闭环

通知状态至少区分：`未读 → 已读 → 处理中 → 已处理/已解决`。

- 仅打开通知：只变为已读，不自动变为已处理。
- 点击“处理”按钮：调用业务接口，成功后写入处理回执。
- 业务对象已失效：展示“对象已不存在/已关闭”，保留历史内容。
- 操作失败：通知仍保持待处理，提供重试和错误原因。

### 7.4 用户偏好

P0 支持：

- 全局免打扰开关和时间段。
- 浏览器通知开关。
- 声音开关。

P1 支持按分类设置渠道：站内、浏览器、邮件、短信。安全类和紧急类通知是否允许用户关闭，必须由系统策略决定。

## 8. P0 管理端功能：公告

### 8.1 公告列表

- 状态：草稿、待发布、已发布、已撤回、已过期。
- 筛选：标题、状态、创建人、发布时间、受众范围。
- 展示发布数、送达数、已读数、处理数（若需要处理）。
- 支持查看、编辑草稿、复制、撤回；已发布内容原则上不可直接覆盖。

### 8.2 新建/编辑公告

必填字段：

- 标题。
- 摘要。
- 正文。
- 通知分类和优先级。
- 受众范围：全部用户、角色、部门、指定用户。
- 发布方式：立即发布或定时发布。
- 生效时间和过期时间。

可选字段：

- 关联页面或业务对象。
- 是否需要确认/处理。
- 浏览器通知、声音和站内展示开关。
- 附件或外部链接（P1，需确认安全策略）。

### 8.3 发布校验与风险控制

- 发布前展示受众数量和预计渠道。
- 目标受众为空时禁止发布。
- 高优先级或安全公告需要二次确认，并记录发布人。
- 已发布公告撤回后，新用户不可见；已读历史是否保留需确认。
- 定时发布需要明确时区、取消和修改规则。

## 9. 消息生命周期与投递

### 9.1 生命周期

```text
草稿 → 已排队 → 投递中 → 已送达 → 已读 → 已处理
                 ↘ 失败 → 重试/终止
```

撤回、过期和对象失效是横向状态，不应通过删除数据实现。

### 9.2 渠道策略

| 渠道 | P0 | 说明 |
| --- | --- | --- |
| 站内通知 | 必须 | 服务端持久化，跨设备同步 |
| 顶部实时提醒 | 必须 | WebSocket/SSE/轮询按现有基础设施选择 |
| 浏览器通知 | 支持 | 需用户授权，可被免打扰抑制 |
| 声音 | 支持 | 仅高优先级默认启用，需处理浏览器自动播放限制 |
| 邮件 | P1 | 需要模板、退订和发送服务 |
| 短信 | P2 | 仅用于安全或强业务场景 |

### 9.3 可靠性要求

- 服务端生成全局唯一 `notificationId`，客户端不得以随机 ID 替代业务幂等键。
- 同一事件重复消费不能产生重复通知。
- 投递失败需要重试次数、最后错误和终止原因。
- 客户端断线重连后按游标补齐，不依赖“只推实时事件”。
- 删除是用户视图隐藏，不直接删除审计和投递记录。

## 10. 核心数据模型（建议）

### 10.1 通知实体

```ts
interface NotificationRecord {
  id: string;
  category: 'task' | 'announcement' | 'message' | 'event' | 'alert' | 'security';
  type: 'error' | 'info' | 'message' | 'success' | 'warning';
  priority: 'low' | 'normal' | 'high' | 'urgent';
  title: string;
  summary: string;
  content?: string;
  source: { module: string; name: string };
  action?: { label: string; target?: string; method?: 'navigate' | 'api' };
  occurredAt: string;
  expiresAt?: string;
  createdAt: string;
  withdrawnAt?: string;
  metadata?: Record<string, unknown>;
}
```

### 10.2 用户通知关系

```ts
interface UserNotificationState {
  notificationId: string;
  userId: string;
  readAt?: string;
  processedAt?: string;
  deletedAt?: string;
  lastDeliveredAt?: string;
  deliveryStatus: 'pending' | 'delivered' | 'failed';
}
```

通知内容与用户状态分离，才能支持多人受众、跨设备同步和独立已读状态。

## 11. 接口契约建议

P0 最少需要：

```text
GET    /api/notifications
GET    /api/notifications/unread-count
GET    /api/notifications/:id
PATCH  /api/notifications/:id/read
PATCH  /api/notifications/read-all
PATCH  /api/notifications/:id/process
DELETE /api/notifications/:id/view
GET    /api/notification-preferences
PUT    /api/notification-preferences
```

管理端：

```text
GET    /api/admin/notices
POST   /api/admin/notices
PUT    /api/admin/notices/:id
POST   /api/admin/notices/:id/publish
POST   /api/admin/notices/:id/withdraw
GET    /api/admin/notices/:id/deliveries
```

列表接口需要返回 `nextCursor` 或明确分页信息；推荐游标分页用于实时消息插入和历史加载。

## 12. 与现有包的演进边界

`@skyroc/web-admin-notification` 建议保持为“通用运行时和展示组件”，不要在包内直接耦合具体业务 API。

### P0 包能力

- `NotificationProvider` 支持受控的初始数据、拉取函数和事件回调。
- 增加 `category`、`status`、`source`、`action`、`occurredAt` 等字段。
- 增加服务端同步适配层：拉取列表、未读数、标记已读、处理和删除视图。
- 支持分页加载、乐观更新、失败回滚和断线补偿。
- `NotificationButton` 保留快捷面板，增加“查看全部”入口。
- `NotificationPanel` 支持分类 Tab、加载更多、错误重试和处理按钮。

### 不放进包内的能力

- 公告编辑器、受众选择和发布工作流。
- 业务权限判断和具体业务对象处理接口。
- 邮件、短信等后端渠道编排。
- 组织、角色、部门数据查询。

## 13. 版本路线

### V1：可用通知中心（P0）

- 站内持久化通知。
- 顶部快捷面板 + `/notifications` 通知中心。
- 全部/待办/公告/消息/异常/安全分类。
- 已读、已处理、删除视图、详情和业务跳转。
- 未读数同步、分页、幂等和基础实时更新。
- 公告创建、发布、撤回和受众范围。
- 浏览器通知、声音和免打扰接入现有包。

### V1.1：可治理和可观测（P1）

- 通知模板和变量校验。
- 邮件渠道。
- 投递记录和失败重试。
- 按分类配置用户偏好。
- 公告统计：送达、已读、处理和失败。
- 通知批量导入/导出仅在有真实业务需求时加入。

### V2：跨渠道消息平台（P2）

- 短信、企业微信、钉钉等外部渠道。
- 复杂规则编排、升级策略和自动重试策略配置。
- 多租户隔离、渠道配额和成本统计。
- 面向业务团队的消息模板市场。

## 14. 页面验收标准

每个页面和状态至少覆盖：

- 首次加载、加载更多和刷新。
- 无通知、筛选无结果、接口失败和重试。
- 未读、已读、已处理、已撤回、已过期。
- 无权限、对象不存在和对象已关闭。
- 重复点击、重复提交和网络断开。
- 桌面 Web、窄窗口和暗色主题。
- 键盘可操作、焦点可见、状态不能只靠颜色表达。

关键验收指标建议：

- 未读数与服务端最终一致。
- 标记已读操作在正常网络下 1 秒内反馈。
- 通知点击到业务页面的成功率可统计。
- 相同事件重复消费不产生重复消息。
- 高优先级通知可追溯到产生事件、受众、投递和处理记录。

## 15. 待确认决策

| 编号 | 决策问题 | 默认建议 |
| --- | --- | --- |
| NOTIFY-001 | 通知中心是否作为独立页面 | 是，顶部面板只做快捷入口 |
| NOTIFY-002 | 实时通道使用 WebSocket、SSE 还是轮询 | 复用现有基础设施；无长连接时先游标轮询 |
| NOTIFY-003 | “删除”是否物理删除 | 否，仅删除用户视图 |
| NOTIFY-004 | 安全通知能否关闭 | 默认不可完全关闭，可关闭非关键渠道 |
| NOTIFY-005 | 公告发布是否需要审批 | P0 先二次确认，审批作为 P1 |
| NOTIFY-006 | 已撤回公告是否保留历史 | 保留历史并显示撤回状态 |
| NOTIFY-007 | 通知正文是否支持富文本 | P0 纯文本/安全 Markdown；富文本和附件 P1 |
| NOTIFY-008 | 多租户和时区 | 在后端租户模型确认后纳入数据契约 |

## 16. 推荐落地顺序

1. 先确认分类、状态、优先级、受众和权限五个核心枚举。
2. 再确认 P0 接口和“通知实体/用户关系”数据模型。
3. 设计通知中心列表、详情、空/错/撤回状态。
4. 将现有包改造成服务端可同步的基础组件。
5. 最后设计公告管理和投递记录，避免先做一个无法追踪效果的发布页面。

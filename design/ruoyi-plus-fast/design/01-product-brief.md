# Skyroc Admin 产品简报

## 1. 基本信息

- 产品名称：Skyroc Admin
- 产品类型：企业后台管理系统
- 当前终端：Web 管理后台
- 当前阶段：产品设计基线
- 当前状态：初版，业务范围待确认

## 2. 产品定位

Skyroc Admin 面向需要统一管理组织、用户、权限、配置和运营数据的企业团队，提供一致、可扩展的后台工作环境。

产品不只是一组通用 CRUD 页面，还需要形成：

- 清晰的角色工作入口。
- 一致的查询、列表、详情和编辑体验。
- 可理解、可追溯的权限和高风险操作。
- 可复用的页面模式和业务组件。
- 能与现有 Skyroc 技术体系对应的设计规范。

## 3. 目标用户

当前初步识别以下用户类型，具体职责和权限见
[02-users-and-roles.md](./02-users-and-roles.md)：

- 企业管理员。
- 系统管理员。
- 业务运营人员。
- 普通员工。
- 审计或安全人员。

以上角色是设计阶段的候选角色，不代表后端已经完成对应角色模型。

## 4. 用户问题

Skyroc Admin 重点解决以下问题：

1. 企业后台功能分散，缺少统一入口和一致操作方式。
2. 用户、角色、菜单和数据范围之间的关系不够清晰。
3. 高频管理操作步骤多，列表筛选和状态反馈不统一。
4. 高风险操作缺少明确影响提示和审计线索。
5. 页面设计与组件代码脱节，后续模块容易出现体验漂移。

## 5. 核心目标

### 5.1 业务目标

- 统一组织、用户、权限和系统配置入口。
- 降低日常运营和系统维护成本。
- 提升配置变更和管理操作的可追溯性。
- 为后续业务模块提供稳定的后台承载框架。

### 5.2 用户体验目标

- 用户登录后能够快速找到与角色相关的任务。
- 列表、详情、编辑和确认交互保持一致。
- 权限不足、操作失败和空数据状态能够被正确理解。
- 高风险操作在执行前明确说明影响范围。
- 常用操作减少不必要跳转和重复输入。

### 5.3 设计与工程目标

- 设计稿与现有设计令牌、主题和组件体系建立映射。
- 使用页面母版降低重复设计和重复开发。
- 页面规格同时描述正常、加载、空、错误和无权限状态。
- 重要产品决定通过设计决策记录长期保存。

## 6. 产品原则

### 6.1 清晰优先

优先帮助用户理解当前位置、数据状态和操作后果，不使用只有视觉效果但含义不清晰的表达。

### 6.2 效率与安全平衡

高频低风险操作应简洁直接；删除、停用、权限变更等高风险操作需要明确确认和结果反馈。

### 6.3 一致但不过度统一

相同业务模式保持一致，不为了表面统一强迫所有页面使用同一种容器或交互。

### 6.4 权限可理解

权限配置需要表达“谁可以对什么执行什么操作”，避免只展示难以理解的权限编码和树形节点。

### 6.5 状态可感知

加载、保存、刷新、失败、空数据和权限不足必须有明确、稳定的反馈。

### 6.6 设计可落地

视觉、交互和组件规范必须能映射到当前 React、Ant Design、Skyroc UI、主题和路由架构。

## 7. 品牌方向

### 7.1 品牌关键词

| 关键词 | 设计含义                                         |
| ------ | ------------------------------------------------ |
| 专业   | 信息层级清晰，反馈准确，不使用随意或戏谑表达     |
| 现代   | 使用清晰排版、适度留白和成熟的交互模式           |
| 克制   | 避免无意义装饰，颜色和动画服务于状态和任务       |
| 科技感 | 通过精确、秩序和系统性体现，不依赖大面积霓虹效果 |
| 可信赖 | 高风险操作、权限和审计信息透明可追溯             |

### 7.2 应避免

- 过度渐变和发光效果。
- 过度卡通的插图和文案。
- 为展示数据而堆叠无业务意义的图表。
- 页面信息过密且缺少层级。
- 过度使用弹窗打断任务。
- 仅通过颜色传达状态。
- 为追求视觉差异而绕开现有组件体系。

## 8. 当前产品范围

当前确定：

- 首先设计 Web 管理后台。
- 账号认证、后台框架、首页、用户与权限、系统配置和审计属于候选核心方向。
- 当前阶段先建立产品和设计基线，再逐模块设计和开发。

当前尚未确定：

- 是否支持多租户。
- 是否正式交付移动 Web。
- 是否包含注册、短信登录和第三方登录。
- 是否包含部门、岗位、字典、公告、文件、定时任务和在线用户。
- 是否正式交付暗色主题和英文版本。
- 数据权限的具体模型。

详细范围见 [03-product-scope.md](./03-product-scope.md)。

## 9. 成功标准

首期成功标准需要在业务范围确认后量化。当前先使用以下设计验收标准：

- 每个首期模块都有明确页面入口和核心任务。
- 每个页面都能追溯到用户目标和功能范围。
- 页面状态和权限状态完整，不只设计理想状态。
- 设计组件能够对应现有代码组件或明确记录新增原因。
- 页面清单、规格、设计稿和开发状态能够统一追踪。
- 不因切换对话或开发环境而丢失关键产品决定。

## 10. 非目标

当前阶段不以以下事项为目标：

- 一次性设计所有可能存在的后台模块。
- 将传统 RuoYi 功能不加筛选地全部复制。
- 让 Web 管理后台与未来 App 页面一一对应。
- 重建与现有主题和 Token 平行的视觉体系。
- 在接口和业务规则未确认前确定全部字段。

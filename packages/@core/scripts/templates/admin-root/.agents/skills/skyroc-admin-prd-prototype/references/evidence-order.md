# 证据读取顺序

目标是先确认当前事实，再设计体验。不要从单一参考项目直接推导最终页面。

## 1. 用户输入

先整理用户明确提供的：

- 目标模块和期望产物。
- 设计文档、PRD、原型、FastAPI、React 和可选参考资料路径。
- 明确要求的页面数量和命名。
- 只做设计还是还要实施生产代码。

用户指定路径是本次任务的首要范围。不要擅自扩大到无关模块。

## 2. 仓库级约束

读取最近的 `AGENTS.md`、设计系统和信息架构：

```text
AGENTS.md
design/ruoyi-plus-fast/design-system.md
design/ruoyi-plus-fast/design/04-feature-map.md
design/ruoyi-plus-fast/design/05-information-architecture.md
design/ruoyi-plus-fast/design/07-page-registry.md
```

只读取与当前页面决策有关的设计文档。已有文档与运行时不一致时，把差异记录为设计或实现漂移。

## 3. 当前 FastAPI

从当前目标后端重新读取：

- `routes.py` 或路由包。
- 请求/响应 schema。
- service、use case、repository 和 model。
- 权限依赖、错误映射，以及与当前模块直接相关的测试或接口文档。

至少核对：

- 实际 HTTP 方法和路径。
- 查询、路径和请求体字段。
- 响应包裹结构、分页结构和字段可空性。
- 权限字符与租户边界。
- 业务校验、受保护记录和错误状态。
- 已实现、部分实现和未实现能力。

接口事实必须来自当前代码、接口文档或运行时证据，不从旧 PRD 反向推断。某类资料不存在时记录证据缺口，不为满足清单而虚构事实。

## 4. 当前 React

如果目标页面或 API 封装已经存在，读取：

- TanStack Router 路由与菜单路径。
- 页面组件、局部组件和查询参数。
- API 类型、请求函数和 TanStack Query 封装。
- 权限组件、字典、状态映射和共用 UI。

记录现有实现可复用部分和与后端不一致之处。不要为了原型顺手修改生产页面。

## 5. 运行时证据

当本地服务、OpenAPI 或已有浏览器会话可用且与任务有关时，核对：

- 实际请求和响应结构。
- 权限不足、空数据和错误状态。
- 当前页面已经呈现的字段、状态和交互。

运行时证据用于确认当前行为，不能替代源码中的权限、业务约束和未覆盖分支。服务不可用时记录未验证项，不阻塞纯设计工作。

## 6. 相邻 PRD 和原型

至少选择：

- 一个业务形态相近的 PRD。
- 一个视觉或交互形态相近的 HTML 原型。

需要在多个既有模式之间取舍时，再读取两个以上样例。选择依据优先于目录距离。例如，带树形筛选的页面应优先参考用户或菜单页面，密钥配置页面应优先参考 OSS 配置，而不是机械参考文件名最接近的页面。

需要提取：

- 文档章节和事实表达方式。
- 页面壳层尺寸、筛选区、表格区、抽屉和弹窗模式。
- 危险操作、空状态、加载状态和反馈方式。
- 移动端降级策略。

## 7. 可选参考资料

仅当用户提供路径，或仓库中确实存在与任务直接相关的历史、外部参考实现时读取。参考资料可以是旧系统源码、产品文档、竞品截图或其他已确认来源。

提取业务边界和设计启发，不复制参考系统的视觉或技术实现。记录：

- 查询条件、数据字段和主要任务。
- 行操作、批量操作和危险操作。
- 系统记录保护、唯一性校验、状态变更和删除约束。
- 与当前 FastAPI、React 和产品规范的差异。

可选参考只能说明来源系统的行为，不能证明当前系统已实现。没有参考资料时跳过本节，不把缺少参考实现视为任务阻塞。

## 8. 证据冲突处理

按以下原则裁决：

1. 当前 FastAPI 和可复现的运行时证据决定“现在能够联调什么”。
2. 当前产品设计系统决定视觉和交互语言。
3. 当前 React 决定已有实现和接入成本。
4. 旧 PRD、旧原型和可选参考资料是历史或外部证据，不是实时接口契约。

不能确定时，在 PRD 中写成“设计假设”或“待后端补齐”，不要伪装为事实。
